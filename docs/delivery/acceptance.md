## 分层证明

单元测试验证格式、状态、解析和数据变换；模拟服务验证协议与错误；模拟器验证构建和大部分 UI；真机验证 Wi-Fi、权限、USB、网络出口和前后台；网络侧记录验证实际流量。高一层结论不能由低一层证据替代。

设备矩阵至少：最低支持 Android、最新稳定 Android、两家 OEM、4 KB / 16 KB 页环境；2.4/5 GHz 路由器，6 GHz 有设备才宣称已验；两类 USB 网卡和有源扩展坞。iOS 二期覆盖最低/最新目标系统与 USB-C iPhone/iPad。没有的设备明确列“未验”。

高级矩阵另外记录 KernelSU Next / Shizuku 版本、内核和 ROM、服务/执行身份、SELinux 保持原策略时的能力。保留无 root / 未授权对照，确保基础工具可用。用户假设已有 root 环境不等于这些组合已经验证；不执行刷机作为本项目的默认测试步骤。

建议性能门槛：运行中 UI 可操作；停止 ≤2 秒；10 分钟 Wi-Fi 会话内存不持续增长；200 个 AP 模拟列表不卡死；100 次任务后无残留监听。iperf 速率与同设备/同网络的可信基线做多次对照，先记录波动范围再设误差阈值，不以一次峰值判断正确。

交付必须重跑至少一个完整链路：选择有线 → 概览 → ping 网关 → DNS → iperf 客户端 → 服务端 → 公网 IP → 公网测速 → 拔线失败 → 切回 Wi-Fi → 信道图。所有主动任务的取消、后台停止和重启恢复也需覆盖。

高级联合链路由 T20 执行：连接 Shizuku Root → 逐项能力检查 → 无 IPv4 DHCP 观察 → ARP 检查 → 抓包陪同 DNS/ping → 停止与导出 → 清当前网络系统 DNS → 临时有线配置 → 未确认恢复 / 确认后限时使用 → 正常恢复；再在独立实验中关闭 Shizuku，验证 recovery_pending、重新授权后的状态核对和恢复。模拟 fixture 可以验 UI，不能证明真实恢复已发生。
